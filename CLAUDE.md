# Rogueout — Project Context

Persistent context for AI-assisted sessions working on this repo. Read this before making architectural changes.

## Vision

**Rogueout** — *Rogue* + *Fallout* — a browser-based, turn-based roguelike combining classic Rogue/NetHack dungeon-crawling (character/glyph tiles, colors, keyboard-driven play) with a Fallout-style open-world structure, rather than pure dungeon-diving. The name is the pitch: the two halves of the design are right there in it.

**The setting is post-apocalyptic Chicago**, New Vegas-style. You wake in Wrigley Field, pulled in off the street by the Vigil, who hold the ruined ball park and are raided regularly by the Wake. Something that matters is in the Loop, far south, and you will not get there for a long time. The city is built **area by area** — each area one seamless map, divided from its neighbours by ruin-choked boundaries that are terrain rather than seams. Wrigleyville is the first and, so far, the only one.

Live at https://staudt.github.io/rogueout/ (repo `staudt/rogueout`, deployed from `main`).

The full design plan (decisions, algorithms, milestone breakdown) lives at
`~/.claude/plans/let-s-build-a-web-based-cheerful-sphinx.md` on the machine that created this repo — treat this file as the durable, in-repo summary of it.

## Stack

- TypeScript + Vite (`vanilla-ts` template). No framework.
- Single `<canvas id="game-canvas">`, monospace glyph-grid rendering (NetHack-style fg/bg per cell). The canvas fills the page between a message log on top and a status line at the bottom; its size in tiles is measured at runtime, not fixed.
- Vitest for unit tests (`npm test`), jsdom environment (needed for DOM-event-driven input tests).
- No backend — all state lives client-side; persistence is a single `localStorage` slot (`rogueout:save`), written every turn and erased on death (permadeath — see M9 below).
- Deploy target: GitHub Pages (static). `vite.config.ts` uses `base: './'` (relative) so the build works unmodified from a plain local static server, `npm run preview`, and a GitHub Pages project subpath alike — no repo-name hardcoding needed.

## Commands

- `npm run dev` — local dev server with HMR.
- `npm run build` — typecheck (`tsc`) + production build to `dist/`.
- `npm run preview` — serve the production build locally.
- `npm test` — run Vitest once. `npm run test:watch` for watch mode.

## Architecture Principles

1. **Data-driven content.** `Tile`, `MonsterData`, `ItemData`, and map files are plain data tables/JSON. Adding a monster/item/tile/map should mean adding a data entry, not touching engine/combat/AI code.
2. **Plain objects, not classes with behavior.** Entities/items/tiles are serializable POJOs. Behavior lives in systems (`CombatResolver`, `AIController`, etc.), not on the objects themselves. This keeps save/load a direct `JSON.stringify`/`parse` and keeps systems unit-testable in isolation.
3. **Pure functions for anything deterministic.** Combat formulas, FOV shadowcasting, durability loss, pathfinding, procedural generation — all pure functions taking explicit inputs (including an injected RNG), so they're testable without mocking the DOM or wall-clock.
4. **The overworld is one seamless map; only genuinely separate places are discrete regions.** Town and wilderness are the SAME `GameMap` — walking from town into the wilds is a plain step, camera scrolling and all (see `ui/Camera.ts`). Dungeon levels are separate `GameMap`s connected by transition tiles (walk onto one → load the linked region at a matching spawn point), NetHack-level-style. This was revised from an original "everything is a discrete region" v1 scope decision after a user explicitly asked for a real open-world feel (see Current Status) — the discrete-region *mechanism* is still there and still used for dungeons, it's just no longer applied to town/wilderness.

## Controls

- **Movement**: Arrow keys = cardinal (N/S/E/W). Diagonal = hold two orthogonal arrow keys within a short chord window (e.g. Up+Right → NE) — no numpad, no yubn keys required. See `src/input/KeyChordDetector.ts`.
- **Mouse in menus**: click any menu row (command menu, inventory, wield/wear/use, shop) to select it, same as Enter. **Mouse on the map** (M7, complete): click an adjacent tile to step/attack that direction; click a distant explored+walkable tile to auto-travel there (animated, ~90ms/step) — interrupts on new input, a newly-visible monster, taking damage, the path becoming blocked, or a region transition. See `input/MouseInput.ts`, `pathfinding/{BFS,AutoTravel}.ts`, `Game.stepAutoTravel`.
- **Keybindings match NetHack conventions** (explicit user request): `,` pick up, `w` wield weapon, `W` wear armor, `q` quaff/use, `i` inventory, `f` fire (placeholder — no ranged weapons yet, shows "You have nothing to fire."), `.` wait, `>`/`<` descend/climb a staircase, `C` character sheet (NetHack uses `^X`; a plain letter is friendlier in a browser), `Esc` game menu. Still to add as content lands: `d` drop, `e` eat, `r` read, `z` zap, `a` apply, `t` throw, `T` take off, `R` remove, `o`/`c` open/close door. The full list is also in-game under Esc → Controls (`ui/screens/HelpText.ts`), which is the one place to update when a binding changes.
- **Stairways need a deliberate `>`/`<`; every other transition still fires on the step.** Standing on a staircase does nothing until you press the key (the tile announcement tells you which: "You see a staircase leading down here. Press > to descend."), whereas walking out of the dungeon's west mouth — an ordinary floor tile — crosses immediately, as it always did. The rule lives in `TurnManager.tryMovePlayer` (skip transitions whose tile is a stairway) + `TurnManager.useStairs`, with `stairwayDirection()` in `Tile.ts` as the shared "is this a staircase" predicate. Besides matching NetHack, this is what stops auto-travel from dropping you into a dungeon just because the path crossed the entrance.
- **`Enter` opens a discoverable command menu** ("What do you want to do?") — every entry shows its direct keybinding right-aligned (e.g. `Wield weapon    [w]`) so the player can learn the keys from the menu instead of memorizing a manual. The first entry is always Pick Up, and its label is contextual: "Pick up" when the tile is empty, "Pick up <item name>" when standing on one. Selecting any entry runs the exact same code path as pressing its key directly (`Game.runCommandAction`) — the menu is a discoverability layer on top of direct keys, never a separate implementation. `Esc` (or selecting nothing) closes it. See `Game.openCommandMenu`/`runCommandAction`.

## Character System (v1)

Fallout SPECIAL stats (Strength, Perception, Endurance, Charisma, Intelligence, Agility, Luck), **fixed preset** at creation — no allocation screen, no XP/leveling in v1 (see Roadmap). Combat is NetHack-style: roll to-hit vs AC, roll damage on hit. Creatures act on a **speed/energy economy** (see below), not one action each per turn. See `src/combat/CombatFormulas.ts` for the concrete formulas (the plan sketched a separate `stats/DerivedStats.ts`; the formulas were small enough to live in one file) (kept intentionally simple and tunable via `src/config/constants.ts`).

Items (weapons/armor) have durability that decreases with use and breaks at 0. No repair mechanic yet.

### Speed

Creatures act on NetHack's model, not one-action-per-turn. Each banks its `speed` in movement
points every player turn and spends `NORMAL_SPEED` (12) per action, so **speed 24 acts twice
while you act once** — closing two tiles to your one, and landing two blows between your swings —
and leftover points carry over, which is what makes fractional speeds work (18 alternates one
action and two). A creature that closes the last tile *and* attacks in the same turn is the
system working: it spent two actions. `MAX_ACTIONS_PER_TURN` bounds the loop so a silly speed
value can't hang a turn. Lives in `AIScheduler.runMonsterTurns` plus `Monster.speed`/`energy`.

The player is still one action per turn; player haste/slow would hang off the same mechanism.

### Damage types and creature tags

Combat is **typed**. A weapon deals one or more `DamagePacket`s (`{ type, min, max }`) and a
defender carries `resistances` (a fraction per type: `0.5` halves, `1` is immunity, a *negative*
is a vulnerability). See `src/combat/DamageTypes.ts`. Types: `cut | pierce | bludgeon | fire |
cold | shock | acid | rad`; the first three are physical and are the only ones Strength adds to.

Creatures carry **open-ended `tags`** — `'living'`, `'undead'`, `'head'`, `'arms'`, `'legs'`,
`'mindless'`, `'amorphous'`, `'sentient'` — rather than a fixed anatomy schema (`hasHead`,
`hasArms`, ...). That was a deliberate choice: a boolean-per-body-part list never stops growing
and forces every system to ask about every field, whereas adding a concept to a tag system means
adding a tag and a rule. Weapons carry `traits` in the same spirit (`'decapitates'`).

The point is that behaviour **emerges from data meeting data**, with no special cases in the
engine. The worked example is `crawling mold`: tagged `mindless` and `amorphous` with
`{ pierce: 1, cut: 0.5, fire: -1 }`. A spear does *literally nothing* to it — there is nothing
inside to puncture — a sword gets half through, and fire does double. Nothing anywhere mentions
mold. Likewise decapitation is one rule: the weapon claims `'decapitates'`, the creature admits a
`'head'`, the killing blow was `cut`. Change any one and it's an ordinary kill.

Rules worth knowing:
- The Strength bonus lands on the **single largest physical component**, not on every component,
  or a two-type weapon would collect it twice for being descriptive about itself.
- A blow that gets through at all does **at least 1** (rounding can't make a real hit free), but a
  fully resisted blow does **exactly 0** and reports `shrugged` — immunity has to mean immunity.
- `AttackResult.type` is the component that did the most damage, so the log can describe the blow
  by what actually hurt. Armour that turns cuts can flip which half of a katana is doing the work.

- **M6 (procedural wilderness) complete.** `src/world/generation/` holds four small pure passes, deliberately separate so each is tunable and testable on its own: `noise.ts` (hand-rolled seeded value noise + fBm — pure functions of `(seed, x, y)`, *not* an RNG stream, so a tile's terrain never depends on the order tiles were generated in), `wilderness.ts` (two independent noise fields — elevation and moisture — thresholded into a biome table: water/rock from elevation, tree/grass/sand from moisture), `poi.ts` (seeded rejection sampling of 2-4 POIs), `stitching.ts` (Bresenham corridor with jittered waypoints), and `connectivity.ts` (flood fill + seal). `maps/overworld.ts` composes them in a strict order that is the whole trick to making a generated world safe to inhabit:

  2. noise terrain over the eastern half,
  3. **stitched road overwrites whatever step 2 produced** along the town→dungeon route, so that route is walkable for *every* seed (no seed rejection, no biasing the noise — just paint over it afterwards),
  4. POIs rejection-sampled onto dry land, spaced apart, off the road,
  5. `sealDisconnectedAreas()` turns every walkable tile unreachable from the town spawn into solid rock, so the finished map has **exactly one** walkable component.

- **Five requests in one pass: turn-grouped messages, kick, wrong-tool feedback, `g` travel, and an inventory action menu.**
  - **One line per player action.** `addMessage` now appends to the current line while a group is open, and `endMessageGroup` starts a fresh one. The group is closed **when the player does something new** (top of the direction/action handlers, map clicks, each auto-travel step) rather than at the end of a turn — that way the world's reply stays attached to what provoked it, and a failed action that consumed no turn doesn't leave the line hanging open. Result: `You graze the pale scorpion. Your cut barely gets through. The pale scorpion grazes you.` Long turns break at `MAX_GROUPED_LINE`.

Knockback stops at walls and at other creatures — and whatever it slams into takes the impact, so a kicked body is a weapon. Kicking also provokes, drops loot if it kills, and never shoves anything onto the player.
  - **Throwing shares kick's code** (`flingItem`): an object flies until it hits someone or runs out of range, does the weapon's own damage or an improvised thump, and **always lands on the map** so a thrown machete is retrievable. Kicking a loose item is the same path with shorter range.

  - **Wrong-tool feedback**: `DamageRoll.resistedFraction` feeds `AttackResult.resisted`, and a blow with 40%+ turned away adds a line ("Wrong tool for the pale scorpion."). - **Scavenging, road patrols, and a frozen-actor bug found by watching them.**
  - **Scavengers pick things up, use them, and give them all back when killed** (`ai/Scavenging.ts`; `MonsterDef.scavenges`, on the Wake and the Restoration). A weapon judged by best-case damage — crude, but a raider hefting a find is exactly that crude, which means **the machete you dropped can come back at you**. Picking up costs the turn, so nobody hoovers a battlefield in one step, and corpses are left where they lie. The point is that a raider who has walked a battlefield *is* the battlefield: killing one late is worth more than killing one early, and it closes a leak where every weapon dropped in a fight lay there forever.
  - **Two patrols walk the road** — four Wake and three Restoration, spawned as bands. The route is the road the generator already carved (`GeneratedOverworld.patrolRoute`, sampled every 6 tiles). That regularity is the entire mechanism: two hostile groups wandering at random on a 70x30 map essentially never meet, whereas two groups walking the same road certainly do.
  - **Patrolling is an instance property, not a species one** (`Monster.patrolIndex`). First attempt put `patrols: true` on the definition, which made the POI ruin guards — also Wake raiders — abandon their ruins and wander off up the road. *This band* walks the road; that raider guards that ruin.
  - **Live, with the player sitting in town doing nothing**: the bands closed from 6 tiles apart, shouted warnings on sighting each other, fought, one side broke and ran, and the road was left with corpses and two dozen dropped items. Nobody scripted an ambush; the road did it.
  - **A real bug, found only by asking why one trooper never moved**: an actor investigating a noise it *cannot reach* was stuck forever, because the arrival check requires getting within one tile and the move can silently fail. It now abandons an errand it can't make progress on. Worth remembering as a shape: any "go to X and then decide" state needs a way to give up.
  - Patrol movement also reuses `moveToward` (detour search and all) rather than the hand-rolled three-candidate step it started with, which wedged patrollers against rocks permanently.
  - **Still to come, per the user: stealing from townsfolk.**
  - Verified by 10 new tests across `tests/loot.test.ts` and `tests/alarm.test.ts` — 277 total.
- **Faction shouts, and no more narrating fights the player can't see.**
  - **"The XXX shouts a warning." is gone.** `narrative/Shouts.ts` gives each faction its own voice, which matters because a shout is the only line most of them ever get: the Restoration bark orders they have no authority to give ("Contact — the Wake, in the open!"), the Wake are simply delighted ("A ragged cheer goes up."), the Reclamation worry about their stock, the Vigil beg everyone to stop. Lines naming the enemy are used when the shouter has someone in their sights, since a directed challenge reads nothing like a general alarm.
  - **A real information leak, reported by the user**: a fight between two patrols in ground they hadn't discovered was narrated blow by blow. The cause is subtle — the world narrated by `isVisible`, which is *terrain* visibility, and under daylight that reaches 60 tiles. You could see a mile of road and still not tell who was hitting whom. Everything the world says about itself (combat, shouts, scavenging, morale, witnesses) now goes through `canSpot`, the same rule the renderer uses to decide whether a creature is drawn at all. If it isn't on screen, it isn't in the log.
  - **What you get instead**: within `HEARING_RADIUS`, "You hear fighting to the east." — direction and nothing else. Sound had to be given a much wider reach than sight (34 vs ~14) or the band where a war is *audible and illegible* would have been two tiles wide and nobody would ever have seen it.
  - **`addMessage` now drops a sentence already present on the current line.** Three raiders spotting you at once produced the same shout three times, and the repeats weren't always consecutive, so the check is `includes` rather than `endsWith`.
  - Verified by `tests/shouts.test.ts` (factions sound distinct with no overlap, enemy naming, no unfilled placeholder for any faction pair, a plain fallback, compass words, and that a distant line carries *no* names or blow-by-blow) — 285 total — plus a live A/B: the same fight at 22 tiles reads "You hear fighting to the east." and at 2 tiles gives the full exchange with shouts.
- **Hearing model made explicit** (user asked whether sound is limited by direction). It's limited by *distance* — but it had been accidentally directional, and the question found it. `ai/Hearing.ts` now owns the rules:
  - **Sound is radial.** Everything else measures distance in Chebyshev steps because that's how movement works, and applying that to noise made the audible area a **square**: a fight was audible about 40% further away on the diagonal than straight ahead. Hearing uses Euclidean distance now. (Verified live: a fight 20 tiles east is audible; the same fight 20 tiles *diagonally* — 28 tiles of real distance — is silent.)
  - **A shout carries further than a scuffle** (`SHOUT_RADIUS` 24, `FIGHT_NOISE_RADIUS` 16). Someone deliberately making themselves heard is a different event from two people grunting at each other, and in open desert that difference is most of what the player has to go on.
  - **Both are tuned against `computeSpotRadius`** (~14 at average Perception) rather than picked freely — too close and the band where a war is *audible and illegible* never gets experienced; too far and the wasteland stops feeling like one. `SHOUT_RADIUS` was briefly 34, which put a third of a 70-wide map in earshot.
  - The resulting layering, measured in a browser: **≤14 you watch the fight, 15–16 you hear fighting and a direction, 17–24 you hear only a shout, 25+ silence.**
  - `SHOUT_RADIUS` also replaced the old separate `ALARM_RADIUS` for NPC reactions, so **the player and the world now hear at the same range** — previously the player heard fighting at 34 tiles while an NPC needed to be within 14 to notice a scream.
  - **Walls still don't stop sound**, deliberately and now tested: hearing round a corner is the entire point of shouting.
  - Verified by `tests/hearing.test.ts` (7 tests, including the diagonal case, the shout/scuffle ordering, both radii exceeding spot range, `SHOUT_RADIUS` staying well under the map width, and sound passing a wall) — 292 total.
- **Stage 0 of the Chicago move: scale remediation.** Invisible in play, and the difference between a city map working and merely being possible. The desert is unchanged; everything here was verified against it *before* any city content exists, which is the point of doing it first.
  - **`src/persistence/MapCodec.ts`** encodes the two fields that scale with map *area*: tiles as run-length pairs over a palette, `explored` as a base64 bitmap. **`visibility.visible` is no longer saved at all** — it's this turn's FOV, recomputed on load, and it was the single largest field in the file. Measured: the real save fell 52.9 KB -> 13.7 KB, and a projected 192x192 city area 662 KB -> 31 KB. That last number is what makes a city affordable: naive, the *fourth* area you visited would have failed to save against a ~5 MB quota.
  - **Areas are the partition, and there is no second chunking layer inside one.** Considered and rejected: chunked tile storage (buys single-digit KB for an indexing layer and a class of bugs where a chunk boundary and a building disagree) and regenerating tiles from `{builderId, seed}` on load (~20 bytes, but makes generator determinism load-bearing, so any later tweak silently reshapes every suspended run). Budget to check rather than hope for: **a fully-explored area must save in under 50 KB.**
  - `SAVE_SCHEMA_VERSION = 2`, and `SavedRegion` is now its own type rather than a reused `RegionState` — which finally makes the long-standing "SaveData is separate from GameState" justification real instead of nominal.
  - **`VisibilityData` holds `Uint8Array`, not `boolean[]`** (300 KB of pointers per region at city scale, for one bit each). Note they are therefore **not JSON-safe** — `JSON.stringify` turns a Uint8Array into an object keyed by index. Nothing should serialize one raw.
  - **Fixed a live save-honesty bug.** `LocalStorageAdapter.write` swallowed its exception, so `saveGame` returned `true` for a write that never happened and "Save and quit" told the player their run was safe before discarding it. `write` now throws, `saveGame` reports honestly, and `Game.flushSave` surfaces it **once per run** (storage that refuses one write refuses them all). Also found on the way: **`hasSave` only checked shape**, so Continue could be offered for a save that then failed to decode — it now does the full load.
  - **Autosave is throttled** (`AUTOSAVE_TURN_INTERVAL = 10`): skipped entirely while auto-travelling (it steps ~11x/second and each step was a full stringify plus a synchronous `setItem`), flushed when travel ends, and always flushed on a region transition, on opening the game menu, and on `pagehide`/`visibilitychange`. The "a save is a suspend" promise is intact — verified in a browser that with localStorage holding turn 21, a reload restored turn 23 with **zero turns lost**.
  - **`findPath` rewritten on flat indices** with `Int32Array` buffers and a generation-stamp visited array (nothing cleared between searches). It now takes a `PathGrid { width, height, isPassable, maxNodes? }`, and **`maxNodes` defaults to uncapped**. The old hard 5,000-node cap was the dangerous part: overrun returned null, callers read null as "no route" and fell back to a straight line, so on a big map long clicks would have *silently* stopped routing around buildings. Pinned by a 250x250 serpentine test that fails with the old cap and passes without it.
  - **`findPathToAny`** replaces `Game.travelToInteract`'s eight separate searches with one — BFS expands in path-length order, so the first goal reached is the nearest, which is exactly what the eight searches were computing the expensive way.
  - **`Actors.actorAt`** ends the real AI cost, which was allocation rather than scanning: `passableForMonster`/`tryMoveMonster` called `livingActors()` — two filters and a spread — *per tile probe*, so one blocked hunter running a 150-node detour allocated 150 throwaway copies of everything alive, every turn. **Deliberately not the position-keyed index the plan sketched**: an index must be kept in step with every move, knockback and death, and going stale means creatures walking through each other — not worth the risk for a few dozen actors when removing the allocation is the whole win. Revisit only if profiling says the scan itself is the problem. It also fixed a real bug in `Game.isPassableIn`, which forgot `hp > 0` on NPCs, leaving a corpse's tile unroutable.
  - **The test suite went from 18.2s to 6.2s** by defaulting the vitest environment to `node` and marking the three files that genuinely need a DOM with `// @vitest-environment jsdom` — it was spending 87% of its time building jsdom for 24 files that never touch it. Also removed an O(V^2) `queue.shift()` from the connectivity flood fill and memoized `procgen.test.ts`'s per-seed generation (it generated the same worlds ~20 times).
  - **Deliberately kept, against the plan**: `pathfinding.test.ts`'s "blocking any one tile strands only a pocket" guard. The plan called for replacing it with an articulation-point pass because ruins forming chokepoints is the *point* of a city — but the city doesn't exist yet, and deleting a live guard for the desert with nothing replacing it would be a straight loss. It goes when the desert does.
  - Verified by `tests/map-codec.test.ts` (20 tests: round trips incl. non-multiple-of-8 bit lengths, every malformed shape -> null, a corrupt run count rejected *before* allocating, and a 400x400 bitmap that would blow the stack of a spread-argument base64 encoder) plus new pathfinding and save-load cases — **322 tests** — and a real-browser run: exact save/load round trip (position, HP, turn, all 1,893 explored tiles), the unload flush, `g`-travel interrupting on a sighting, and monsters still pathing.
- **Stage 1 of the Chicago move: the `door` tile, and regions built from recipes.** Also shipped on the desert, and proven on the general store, before a city depends on any of it.
  - **New tile `door` (`+`), walkable and *opaque*.** Opaque is the deliberate half: you should not be able to read a building's interior off the street through its doorway. FOV always marks the viewer's own tile visible, so standing in a doorway still works.
  - **Doors are deliberate, exactly like stairs.** `stairwayDirection` generalised to `transitionKind(tileId)` / `isDeliberateTransition(tileId)` in `Tile.ts`; `TurnManager.useStairs` -> `useTransition`, `stairwayUnderPlayer` -> `transitionUnderPlayer`. Walking onto a door does nothing but announce itself. The reason is the same one that applies to stairs and matters far more in a city: **auto-travel must never route you *through* a building because cutting the corner was two steps shorter.** A doorway answers to **both `>` and `<`** — there is only ever one transition on a tile, so nothing needs disambiguating, and making the player work out which side of a door they're on would be friction with no decision behind it.
  - **Transitions moved from `RegionDef` onto `RegionState`**, along with `name` and `arrival`. A generated city's doorways aren't known until generation has run and must survive a reload, so a static table can't own them. `REGIONS` is still the *definition* table; it is no longer the runtime source of truth, and the five places that did `REGIONS[id]?.name ?? id` now read the region they're already holding.
  - **`RegionRecipe` + `REGION_BUILDERS`** (`world/regions/RegionTypes.ts`): a region with no entry in `REGIONS` at all, described by `{ builderId, regionId, name, seed }`, built on demand. The recipe travels on the `RegionTransition` that points at it, so it **rides into the save** — which is the whole point. Registering interiors into `REGIONS` as they're generated was the obvious alternative and is wrong for a reason already recorded in this file for the morale `Map`: module-level mutation does not survive a page reload and leaks across New Game. Resolution order in `ensureRegionLoaded` is already-loaded -> handcrafted -> recipe -> throw, and **recipe comes last on purpose**: rebuilding a place you've visited would quietly resurrect everything you killed in it.
  - **The general store is now a solid block with one real door**, and Maren keeps the counter inside (`maps/storeInterior.ts`, built by the `storeInterior` recipe). Stamping buildings solid rather than hollow is not cosmetic — it is what will keep the city generator tractable, since a curated-interiors-only world has no accidental interiors to seal, only rooms somebody authored.
  - `RegionTransition` also gained `announce` and `turnCost`. `announce` earned itself immediately: leaving the shop was printing the desert's *arrival* line ("You come up into the open"), which is written for surfacing from the tunnels and reads absurdly when you've stepped out of a shop onto a street you were just standing on. `turnCost` is how the city will elide the ~10 blocks between landmarks; it has no content using it yet and is **tested anyway**, because machinery that is written but never exercised has quietly stopped working by the time somebody needs it.
  - **`region-connectivity.test.ts` now covers recipe-built regions too**, not just `Object.values(REGIONS)`. An interior nobody can cross is exactly as broken as a walled-off town, and the recipe-built ones are easier to overlook precisely because they aren't listed anywhere.
  - Verified by `tests/doors.test.ts` (14 tests — walking onto a door doesn't cross, both keys work, the interior persists across visits *and* is not rebuilt from its recipe, an unknown region or builder throws, and the load-bearing one: **save with the interior never entered, reload, and the door still opens into it**) — 338 tests — plus a browser run of the whole loop: step onto the door without crossing, `>` in, trade with Maren, `<` back out onto the street, then reload and Continue with the interior and its shopkeeper intact.
- **Stages 2 and 3 of the Chicago move: the city generator, Wrigley Field, and the end of the desert.** The game now opens in ruined Chicago. `world/generation/city/` and `world/landmarks/` are new; `maps/overworld.ts` and its town are deleted.
  - **Streets are authored, blocks are procedural.** The central opinion, and the reason a generator can put Wrigley Field at Clark and Addison at all: an `AreaDef` declares its named streets and the generator fills between them. **Blocks are the complement of the lattice, derived and never declared** — a hand-written block list would be a second source of truth that silently disagrees the moment a street moves.
  - **Connectivity is reasoned about on a street graph of a few dozen nodes, never on the 37,000-tile grid.** `StreetGraph.bury(segment)` *refuses* any stretch whose loss would disconnect the lattice, so the damage pass can propose whatever the noise field asks for and never has to understand connectivity itself. The desert's approach — wreck it, then repair and seal — works when a map is mostly open; a city is mostly solid, and a seal pass running afterwards would happily brick up half a district. The map is connected **by construction**; the repair and the final assert exist to prove it.
  - **`CityCanvas` enforces a protect mask on every write**, rather than trusting pass ordering. Damage is the one pass that writes everywhere, and ordering alone holds only until somebody adds a pass or reorders two — at which point a ballpark quietly grows a hole in it. Two different seeds now produce byte-identical Wrigley Fields, which is a test.
  - **Buildings are stamped solid** (a `brick` ring around a `ruin` core), never hollow. This follows from curated-interiors-only and buys much more than content scope: with no accidental interiors anywhere, the seal pass has almost nothing to do and the only rooms that exist are ones somebody authored. It is the difference between a tractable generator and an intractable one.
  - **New tiles**: `street` (`.`), `brick` (`#`), `rubble` (`:`, **walkable** — a collapsed building is a shortcut through a block, not a longer wall), `ruin` (`*`, impassable, and what district boundaries are made of). All with solid backgrounds, per the lesson the sand background taught: a city drawn as bare glyphs on black reads as a wireframe maze.
  - **Two tuning findings, both from measurement rather than taste.** Blocks came out square until the street table was fixed: a Chicago block is **660 x 330 ft = 44 x 22 tiles, long axis east-west**, so avenues sit ~48 tiles apart and streets ~26, and the park's block is a deliberate double. And the first damage thresholds left the map **50% walkable with more rubble than street**, which read as open ground with some walls in it — the opposite of a city, and it quietly undid the premise that streets are how you get around. Both are now asserted across three seeds rather than eyeballed.
  - **Wrigley Field (40x40) is the settlement, and it is seamless** — no region, no transition. You walk in through the marquee at Clark and Addison and the bowl opens up in front of you: brick outer wall, `floor` concourse, `rubble` grandstand, and a `grass` field that is the only green for miles. Two upper-deck sections are **authored** as collapsed, so "the section on the third-base side" can mean something. Eight NPCs across the Vigil, Reclamation and settlers live inside; the Restoration are pointedly *not* here, because they hold the roads south, which is a reason to go.
  - **The Addison station re-homes `dungeon-1`/`dungeon-2`**, so that content survived the move rather than being thrown away, and it anchors the elevated line — drawn over the blocks but never over the streets, because you walk *under* an L. The tracks are impassable and visible from a long way off, and they point at the Loop.
  - **The clubhouse, behind a door under the stands, is the city-side outing for region recipes.** Proving it there rather than on the marquee is deliberate: the marquee is seamless and should stay that way, so the newest machinery gets the smaller target.
  - **The chokepoint test was finally replaced**, as Stage 0 said it would be once the city existed. "No single creature can cut the world in half" is the *wrong* test for a city — ruins forming chokepoints between districts is now the point. In its place: **no single body may hold the only route from where you wake to any transition**, asked exactly rather than sampled (a separating tile must lie on every route, so testing the tiles of one BFS path is both cheap and complete). **It failed on its first run and found a real flaw**: the Addison station had a single doorway, so one creature standing in it locked the player out of the service tunnels entirely. The station now has two street entrances.
  - **A content wart of the same shape as Stage 1's**, caught by reading the log rather than by a test: coming up from the tunnels printed Wrigleyville's *arrival* line about the ball park bowl, while standing on Addison nowhere near it. The area's arrival line is now generic and the tunnel mouth carries its own `announce`.
  - **The desert is gone**: `maps/overworld.ts`, its eleven-NPC town, the store interior and the overworld-composition tests. **`noise.ts`, `wilderness.ts`, `poi.ts`, `stitching.ts` and the `sand`/`grass`/`tree`/`water` tiles all stay**, with their unit tests — the city already uses the last two, and the first two are waiting for the evaporated lakebed. What went with the desert was only the composition of them into one particular map.
  - Measured: generation **~150 ms**, and a **fully-explored 192x192 area saves in 44.4 KB** against the 50 KB budget Stage 0 set — now an assertion rather than a one-off measurement, since that is what quietly regresses when somebody adds a field to a region.
  - Verified by `tests/city-generation.test.ts` (24 tests across three seeds: determinism, block proportions, the graph refusing to disconnect itself, one walkable component, every transition and inhabitant reachable, the street/rubble ratio, byte-identical landmarks, the L crossing every east-west street, and a generation-time guard) — **343 tests** — plus a real browser run at 1440x900: **screenshots judged for legibility before correctness**, then waking in the bowl, out through the marquee onto Addison, the clubhouse door both ways, trading with Maren, down the station stairs into the tunnels, back up onto the street, and a reload restoring all three regions.
  - **Known and deliberate**: the southern boundary is solid `ruin` with nothing behind it. The `AreaEdge` mechanism for joining areas is designed but not built — with no second area it would be an untested abstraction. **The bestiary is still desert-flavoured** (`dustRat`, `sandSkink`, `duneRunner`), which is its own content pass.
  - **The street table is a first draft.** What is solid is the part everyone knows — the park bounded by Clark, Addison, Sheffield and Waveland, the marquee at Clark and Addison, the L and its Addison station just east. The cross streets are general knowledge rather than street-level, and `maps/wrigleyville.ts` says so: **it is data, meant to be corrected.**

What comes next is content and systems, not scaffolding — see the Roadmap below, and the deferred narrative-message-log pass noted in M5.

## The world

Post-apocalyptic desert. Four human factions, settled with the user:

- **The Restoration** — militia restoring order with military discipline, and fundamentally
  corrupt. Holds the roads. The only faction that `keepsOrder`: answers trouble anywhere in
  earshot instead of only what happens in front of it.
- **The Wake** — accepts the world is over and is throwing it a funeral. Anarchic, hostile to
  almost everyone, and the one human faction the town is at war with.
- **The Reclamation** — scavengers who believe anything made before the end is worth more than
  anything made since. They trade — with anyone, the Wake included, which is why they aren't
  hostile to them. *Scrappers* is the street term for them.
- **The Vigil** — a selfless order that finds water, purifies it and gives it away, and sits with
  the dying. Friendly to the player, and pacifist to the point of objecting when you beat a raider.
- **The settled** — people who live here and belong to no organisation.

**The four settled factions are all friendly with each other.** The Restoration and the
Reclamation still dislike each other, but that is **temperament, carried in what they say**, not
enmity in the standings table. Modelling the rivalry as neutrality was tried and reverted: it made
the Restoration the one faction that neither helped anyone nor was helped by anyone, which read
exactly like the bug it wasn't — the user reported it twice. A town looks after its own; if that
tension needs to become mechanical later, reputation is the place for it, not a permanent table.

Plus ecology, which is not politics: **wildlife** (hostile to nobody — a creature that hunts
belongs to **predators** instead, which is the entire difference between a skink and a dune
runner) and **the feral** (ghouls, hostile to everything with a pulse).

## Agreed design direction (discussed and signed off; build in this order)

1. ~~**Damage types, tags, resistances**~~ — done, see Character System above.
2. ~~**Factions and disposition**~~ — done, see the status entry. Still open from this stage:
   attackable NPCs, standing that *changes* with what the player does, and allies. Original note:
   Critically: **standings are relations between factions, not a
   creature's attitude toward the player.** This came out of the user wanting large open battles
   ("a desert war you're just one part of"). With faction-vs-faction standings, a battle is pure
   content placement — drop thirty raiders and thirty militia in a region with their factions at
   war and let the AI run; nobody scripts a battle. With player-relative disposition it's
   impossible without scripting. Cheap now, expensive to retrofit — do not shortcut this.
   Ship hostile/indifferent first; **allies are their own piece of work** (follow-AI, targeting,
   and they will absolutely park on the one-tile causeway).
3. **Skills, use-based.** Gains flow to the used skill and partly to a parent (`melee`), so
   cutting lifts piercing a little — the graph is a data table. Designed against grinding from
   day one: gain scales with how dangerous the target was, diminishing returns as the skill rises,
   and gains on *meaningful events* (a kill, a hit on something that could hurt you), never per
   swing. SPECIAL stays innate and fixed; skills are learned and fluid — Fallout's split, kept clean.
4. **Classes as starting kits, not cages.** A class sets opening SPECIAL tilt, starting skill
   weights and gear; everything after is use-based. Elder Scrolls' model — identity without a cage.
   Needs a character-creation screen, which `ScreenManager` already supports.
5. **Firearms.** Deliberately last: the expensive part is ranged targeting (line of fire, target
   selection), not the gun. Design intent is *unreliable, loud, ammo-starved* rather than weak —
   improvised ammunition (teeth, salt), jams and misfires, noise that draws attention. Weak-and-safe
   is just a worse sword; strong-and-risky is a decision. `f` is already stubbed.

Also agreed: a **goal** is wanted (an Amulet-of-Yendor-style direction, not a plot) and quests
should be **faction objectives, not authored narrative chains** — do a thing, standing shifts,
different people shoot at you later. That keeps it non-linear, and lets the war and the goal be
the same thing: everyone is fighting over what you came for.
